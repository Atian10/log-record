## 一、架构总览

### 1.1 设计目标

- **跨平台**：一套核心代码支持 Android / Windows 桌面 / Windows 服务器 / Linux 服务器
- **可复用**：作为基础组件被其他项目引用，业务方无需重复造轮子
- **零平台依赖核心**：`log-core` 纯 Java SE 实现，所有平台共用
- **平台适配层**：平台相关能力（Room/JDBC/Logcat）通过适配模块注入

## 二、模块划分

### 2.1 模块清单

| 模块 | 职责 | 依赖 | 平台 |
|------|------|------|------|
| `log-core` | 核心接口、引擎、查询、清理（纯 Java SE） | 无 | 全平台 |
| `log-android` | Android 平台适配（Room + Logcat） | log-core | Android |
| `log-desktop` | 桌面/服务器适配（JDBC SQLite + Console） | log-core | JVM |
| `log-sample` | 桌面/服务器使用示例（纯 Java） | log-desktop | JVM |
| `log-sample-android` | Android 应用示例 | log-android | Android |

### 2.2 模块依赖关系

```
log-sample (桌面/服务器示例)
  └── log-desktop
        └── log-core

log-sample-android (Android 示例)
  └── log-android
        └── log-core
```

**依赖规则**：
- `log-core` 不依赖任何平台模块（强制）
- 平台模块单向依赖 `log-core`
- 业务项目只依赖需要的平台模块

## 四、核心接口设计

### 4.1 写入接口 ILogger

```java
public interface ILogger {
    // 基础级别写入
    void d(String tag, String message);
    void i(String tag, String message);
    void w(String tag, String message);
    void e(String tag, String message);
    void f(String tag, String message);

    // 携带异常（便捷方法，内部拆为两条独立记录）
    void e(String tag, String message, Throwable throwable);
    void f(String tag, String message, Throwable throwable);

    // 完整参数写入
    void log(LogLevel level, String type, String tag, String message);
    void log(LogLevel level, String type, String tag, String message, Map<String, String> userFields);
    void log(LogLevel level, String type, String tag, String message, Throwable throwable);
    void log(LogLevel level, String type, String tag, String message, Map<String, String> userFields, Throwable throwable);

    // 异常独立写入
    void recordException(Throwable throwable, String tag);

    // 控制方法
    void flush();
    void shutdown();
}
```

### 4.7 LogManager 全局门面（核心入口）

LogManager 是业务方唯一接触的入口，聚合写入、查询、导出、清理、状态、配置更新全部能力。内部委托给 ILoggerEngine、IStorage、IExceptionStorage、Exporter 等组件。

```java
public final class LogManager implements ILogger {

    // ===== 初始化 =====
    // 平台无关入口：仅接收 LogConfig，由调用方先构建好 Storage 注入
    public static synchronized LogManager init(LogConfig config);
    public static LogManager get();                               // 获取单例
    public static boolean isInitialized();                        // 是否已初始化

    // ===== 写入（实现 ILogger，方法清单见 4.1）=====
    // d / i / w / e / f / log(...) / recordException(...) / e(tag,msg,throwable) / f(tag,msg,throwable)

    // ===== 查询 =====
    public List<LogRecord> queryLogs(LogQuery query);
    public List<ExceptionRecord> queryExceptions(ExceptionQuery query);
    public LogStatistics statistics(LogQuery query);

    // ===== 导出（委托给 Exporter，分页查询避免 OOM）=====
    // 编码从 LogConfig.getExportEncoding() 读取，调用方无需传入；返回导出条数
    public int exportLogs(LogQuery query, ExportFormat format, String filePath,
                          ExportCallback callback);
    public int exportExceptions(ExceptionQuery query, ExportFormat format, String filePath,
                                ExportCallback callback);

    // ===== 清理 =====
    public void cleanNow(CleanCallback callback);
    public int cleanBefore(long timestamp);
    public int cleanByCount(int keepCount);

    // ===== 状态 =====
    public LogStatus getStatus();
    public String getLastWarning();                               // 内部告警最近一条快照

    // ===== 配置更新 =====
    public LogConfigUpdater getConfigUpdater();

    // ===== 控制 =====
    public void flush();
    public void shutdown();                                       // 默认限时等待；资源收尾完成后才允许重新 init
}
```

> 注：Android 平台入口在 `AndroidLogInit.init(Context, LogConfig.Builder)`，桌面/服务器入口在 `DesktopLogInit.init(String dbPath, LogConfig.Builder)`，两者内部调用 `LogManager.init(LogConfig)`。

**设计要点**：
- LogManager 持有 ILoggerEngine、IStorage、IExceptionStorage、Exporter、CleanTask 的引用
- `init()` 时根据 LogConfig 创建引擎、Storage、Exporter
- 查询/统计方法委托给 IStorage（日志库场景通常只有一个 DB Storage）
- 导出方法委托给 Exporter，编码从 LogConfig 读取（配置归一化）
- 关闭结果 isFullyTerminated() 或原实例 isTerminated() 为 true 后，才允许业务方重新 init
- `get()` 未初始化时抛出 IllegalStateException

### 4.8 辅助类型定义

#### QueueFullPolicy（队列满策略枚举）

```java
public enum QueueFullPolicy {
    DROP_OLDEST,    // 丢弃最旧日志（默认）
    DROP_NEWEST,    // 丢弃最新日志（当前提交的）
    BLOCK           // 阻塞等待（慎用，可能阻塞业务线程）
}
```

#### LogStatus（库状态类，非枚举）

```java
public final class LogStatus {
    private final State state;          // NORMAL / DEGRADED / ERROR / SHUTDOWN
    private final String message;       // 状态描述
    private final long warningCount;    // 内部告警计数

    public enum State { NORMAL, DEGRADED, ERROR, SHUTDOWN }

    public boolean isNormal();
    public boolean isDegraded();
    public boolean isError();
    public boolean isShutdown();
    public String getMessage();
    public long getWarningCount();
}
```

#### LogEntry（队列包装类，区分日志/异常）

```java
public final class LogEntry {
    private final int type;             // 0=LogRecord, 1=ExceptionRecord
    private final LogRecord logRecord;
    private final ExceptionRecord exceptionRecord;

    public static LogEntry of(LogRecord record);
    public static LogEntry of(ExceptionRecord record);

    public boolean isLogRecord();
    public boolean isExceptionRecord();
    public LogRecord getLogRecord();
    public ExceptionRecord getExceptionRecord();
}
```

**批处理分类机制**（解决 P11 防凑数钩）：
- 队列类型为 `BlockingQueue<LogEntry>`
- 工作线程取出 LogEntry 后按 `isLogRecord()` 分类
- 攒批时分别收集到 `List<LogRecord>` 和 `List<ExceptionRecord>`
- 达到批处理阈值或超时后，分别调用 `IStorage.writeBatch()` 和 `IExceptionStorage.writeBatch()`

## 五、配置设计

### 5.1 LogConfig

```java
public final class LogConfig {
    // ===== 静态配置（初始化后建议不修改） =====
    private final IStorage storage;                  // 单一存储（不是 List，平台适配层用装饰器聚合多通道）
    private final IExceptionStorage exceptionStorage;
    private final int queueCapacity;                 // 异步队列容量
    private final QueueFullPolicy queueFullPolicy;
    private final int batchSize;                     // 批量写入阈值
    private final long batchIntervalMillis;          // 批量写入周期

    // ===== 动态配置（可运行时修改） =====
    private final boolean consoleEnabled;            // 控制台开关（平台适配层装饰器内部读取，LogManager 自身强制 false）
    private final boolean captureMethodLine;         // 方法名/行号捕获（默认 false）
    private final String versionTag;                 // 版本标签（语义由业务方自定义，可空）
    private final IFormatter formatter;              // 格式化器（null 表示用 DefaultFormatter）
    private final ILogFilter logFilter;              // 日志过滤器（单数，非 List）
    private final CleanPolicy cleanPolicy;
    private final CleanPolicy exceptionCleanPolicy;  // 异常表独立清理策略
    private final ExportEncoding exportEncoding;     // 导出编码

    // Builder 模式
    public static class Builder {
        public Builder storage(IStorage storage);
        public Builder exceptionStorage(IExceptionStorage storage);
        public Builder queueCapacity(int capacity);
        public Builder queueFullPolicy(QueueFullPolicy policy);
        public Builder batchSize(int size);
        public Builder batchIntervalMillis(long millis);
        public Builder consoleEnabled(boolean enabled);
        public Builder captureMethodLine(boolean capture);
        public Builder versionTag(String tag);
        public Builder formatter(IFormatter formatter);
        public Builder logFilter(ILogFilter filter);
        public Builder cleanPolicy(CleanPolicy policy);
        public Builder exceptionCleanPolicy(CleanPolicy policy);
        public Builder exportEncoding(ExportEncoding encoding);
        public LogConfig build();
    }

    // 基于已有配置创建 Builder（用于运行时修改时拷贝）
    public static Builder builderFrom(LogConfig source);
}
```

> 实现说明：
> - 平台适配层（AndroidLogInit/DesktopLogInit）会自动注入 `storage`/`exceptionStorage`，业务方在 Builder 中无需手动设置
> - 多通道输出（DB + Console）通过**装饰器模式**实现（LogcatStorage/ConsoleStorage 包装 DB Storage），而非 `List<IStorage>`
> - LogConfig 为不可变对象，运行时修改通过 `LogConfigUpdater` 以 `AtomicReference<LogConfig>` CAS 整体替换实现并发可见性

### 5.3 LogConfigUpdater（运行时动态修改）

```java
public final class LogConfigUpdater {
    // 持有 AtomicReference<LogConfig>，通过 CAS 整体替换实现线程安全
    public LogConfigUpdater(LogConfig initialConfig);
    public LogConfig get();

    // 各 update 方法内部循环 CAS 替换，无需手动 apply()
    public void updateConsoleEnabled(boolean consoleEnabled);
    public void updateCaptureMethodLine(boolean captureMethodLine);
    public void updateVersionTag(String versionTag);
    public void updateFormatter(IFormatter formatter);
    public void updateLogFilter(ILogFilter logFilter);
    public void updateCleanPolicy(CleanPolicy cleanPolicy);
    public void updateExceptionCleanPolicy(CleanPolicy exceptionCleanPolicy);
    public void updateExportEncoding(ExportEncoding exportEncoding);

    // 整体替换（高级用法，仅允许修改动态配置项）
    public void set(LogConfig newConfig); // 静态配置变更抛 IllegalArgumentException
}
```

**可修改项**：versionTag、captureMethodLine、consoleEnabled、formatter、logFilter、cleanPolicy、exceptionCleanPolicy、exportEncoding

**不可修改项**：storage、exceptionStorage、queueCapacity、queueFullPolicy、batchSize、batchIntervalMillis（需重新 init）

> ⚠️ **set() 静态配置校验（v1.5+）**：`set()` 方法会校验新配置的 静态配置（storage/exceptionStorage/queueCapacity/queueFullPolicy/batchSize/batchIntervalMillis/capacityCoordinator/databaseOperationGuard/databaseCloser）是否与当前配置一致。若检测到变更，抛出 `IllegalArgumentException`，异常消息形如 `queueCapacity cannot be changed via set(); re-init LogManager instead`。这是因为静态配置变更需要重新初始化引擎（重建队列、重启 worker），通过 `set()` 静默替换不会触发引擎重建，会导致配置与实际行为不一致。如需修改静态配置，请保留原实例，调用带时限的 shutdown，并确认 isFullyTerminated() 或原实例 isTerminated() 后再重新 init。

> 修改 `cleanPolicy` / `exceptionCleanPolicy` 后，配置对象通过 CAS 替换，但不会自动通知 `CleanTask`。业务方须对同一管理器调用 `refreshCleanPolicies()`，由其调用 `CleanTask.updatePolicies()` 同步两表策略。原先禁用而未启动的调度，在刷新发现新策略至少有一项启用时启动。

**并发可见性说明**（解决 P12 防凑数钩）：
- LogConfig 本身为不可变对象（`final class` + `final` 字段），`LogConfigUpdater` 持有 `AtomicReference<LogConfig>`，通过 CAS 整体替换保证并发可见性，避免字段级 `volatile` 的中间态问题。
- 工作线程在构造 `LogRecord` 时通过 `LogConfigUpdater.get()` 读取最新配置的 `versionTag`、`captureMethodLine` 等，实现运行时动态修改生效。

### 6.3 异常隔离

- 每个 Storage 独立 try-catch
- 单个 Storage 异常不影响其他 Storage
- 异常记录到内部告警计数器
- 不向业务线程传播异常

### 6.4 接收序号与 flush 等待边界

每条准入记录分配单调递增序号；stateLock → flushLock 固定锁序，TreeSet 保存真实待完成序号。批次保留每个输入的类型与序号，删除 pending 成功才更新终态计数，因此队列丢弃形成的空洞不会再次计数。

`flush(timeout)` 捕获当时目标序号，仅等待目标及之前的 pending 归零。FlushResult 保留等待增量 saved/failed/dropped/unknown，并增加包含历史的 targetSaved/targetFailed/targetDropped/targetUnknown；COMPLETED 是处理终结，isAllPersisted 才确认全部目标已保存。旧式部分批次汇总无法分配到跨目标子集时，该子集计 UNKNOWN，不推测具体记录。

JDBC 只在提交前失败且确认回滚、恢复连接成功后逐条重放一次。commit 抛错按 UNKNOWN 隔离连接，不回滚后重放；commit 正常返回而 statement.close 或连接恢复失败仍保留 SAVED 证据。

关闭按 RUNNING → CLOSING → CLOSED 推进，零时限不等待，后台唯一收尾者等待引擎、清理和活动操作后关闭数据库。DatabaseOperationGuard 的统一锁序为：存活许可 → 两表导出锁（log→exception）→ 维护锁 → JDBC/Room 内部锁。快照持有整个复制期的存活许可，格式化及回调在许可外。平台 owner 原子发布/比较清除，旧实例不能清掉新所有者；CLOSED 在单例身份清除后发布。

## 八、导出设计

### 8.1 导出器架构

Exporter 由 LogManager 在 `init()` 时创建，持有 IStorage 和 IExceptionStorage 引用。业务方不直接创建 Exporter，通过 `LogManager.get().exportLogs(...)` / `exportExceptions(...)` 调用；formatter 与编码在每次导出开始时从当前配置捕获（运行时更新 formatter 后的下一次导出生效，单次导出全程一致）。

```java
public class Exporter {
    private final IStorage storage;
    private final IExceptionStorage exceptionStorage;
    private final IFormatter formatter;   // 构造缺省；可被每次调用的 formatter 参数覆盖

    // 按次 formatter 重载（快照捕获，单次导出一致）
    public int exportLogs(LogQuery query, ExportFormat format, ExportEncoding encoding,
                          IFormatter formatter, String filePath, ExportCallback callback);
    public int exportExceptions(ExceptionQuery query, ExportFormat format,
                                ExportEncoding encoding, IFormatter formatter,
                                String filePath, ExportCallback callback);
}
```

> 注：Exporter 采用同步执行，由调用方决定是否异步（如包在业务线程中）。Android 上导出
> （数据库 + 文件 IO）禁止在主线程调用。

### 8.2 一致性快照导出机制（防 OOM + 集合一致）

导出分三阶段（替换旧的 OFFSET 分页，修复并发写入/清理下的重复与遗漏）：

```
1. 快照复制（持有导出读取保护）
   openExportSnapshot(query) 捕获目标表已提交最大 ID 边界与匹配数量；
   按 (timestamp, id) 双键游标分批（每批 1000 条）复制到本次私有的
   原始快照临时文件（JSON 行，UTF-8）。期间允许追加写入（边界外不进入导出），
   目标表清理被读写锁互斥推迟；导出快照复制中容量维护返回 POSTPONED。
2. 格式化输出（已释放读取保护）
   从快照文件读取记录 → formatter 格式化 → 写入目标目录内本次专属临时文件；
   formatter 与回调的耗时不在保护范围内。单条格式化失败即终止整个导出。
3. 发布
   输出文件完整关闭后 rename 原子替换目标（Windows 经反射隔离的 java.nio
   Files.move ATOMIC_MOVE + REPLACE_EXISTING；Android API 21 使用 Os.rename）。失败保留原目标，
   不先删除旧文件再移动。
```

**失败契约**：任一必要步骤失败 → onFailure 至多一次、本次临时文件按归属清理、原目标不受损；
`onSuccess` 仅在发布完成后触发；回调自身抛错被捕获并单独记录（`getLastCallbackError()`），
不影响结果也不触发相反终态；线程中断视为取消并清理。

**存储适配**：`IStorage/IExceptionStorage.openExportSnapshot` 默认抛
`UnsupportedOperationException`（自定义存储需提供快照适配才能导出，不回退 OFFSET）；
内置 Room/JDBC 实现快照，Console/Logcat 装饰器转发。读取失败抛 `ExportSnapshotException`
（严格区分"读取失败"与"没有数据"）。

## 九、清理设计

### 9.1 清理触发时机

| 触发方式 | 说明 |
|---------|------|
| 定时触发 | 后台 ScheduledExecutorService 定时执行（默认每天一次） |
| 手动触发 | 业务方调用 `cleanNow()`（Android 上禁止主线程） |

### 9.2 两阶段清理流程

清理分**表级规则**与**全库容量阶段**两个层级，每轮清理先执行表级规则，再独立执行容量阶段：

```
表级规则（每张表独立）：
1. 检查 CleanPolicy.enabled
2. 按天数清理：DELETE WHERE timestamp < (now - keepDays)
3. 按数量清理：若 count > maxRecordCount，保留最新 N 条
（表级不再按容量删除；旧 maxDbSizeMB 仅作为预算迁移来源）

全库容量阶段（存在有效预算且配置 CapacityCoordinator 时）：
1. 非阻塞获取两表导出保护写锁：快照复制中返回 POSTPONED 推迟
2. 先记录数据库相关文件总长的 bytesBefore 基线（主文件 + -wal + -shm + -journal）；
   再执行 checkpoint/回收，并在回收后的 checkpoint 确认完成后重新度量
3. 校验 checkpoint 三列；忙碌/失败立即停止。读取实际 auto_vacuum：
   INCREMENTAL 且有空闲页时完整执行 incremental_vacuum；无空闲页则进入删除判定；
   其他模式有空闲页且具备约两倍主文件额外空间时执行 VACUUM
4. 仍超限则按参与表中全局最旧记录删除一批（(timestamp, 固定表顺序, id)，
   每批 ≤500），确认提交后回收空间、校验 checkpoint 并重新度量，达标即停
5. 回收失败/忙碌/空间不足/无物理进展 → 停止容量删除并进入跨轮仅恢复状态；
   恢复轮次零删除，无进展状态须观察到体积下降或达标；状态不跨进程持久化。
6. 无可删数据/工作预算耗尽 → NOT_MET；度量未知为 -1，不伪装成零。
```

**预算来源与迁移**：`LogConfig.databaseMaxSizeMB`（null=按旧值迁移 / 0=显式禁用 / 正数=预算），
冲突在 `build()` 校验；参与表按迁移规则确定，禁用策略表始终受保护。一个数据库只装配一个
容量协调器（JdbcCapacityCoordinator / RoomCapacityCoordinator，平台初始化层注入）。

**结果契约**：`CleanResult`（MET/NOT_MET/POSTPONED/FAILED + 各表删除数、前后字节、目标、停止原因）；
仅 MET（或没有容量阶段）可触发整轮成功；其他结局触发失败回调。手动/定时轮次以 roundLock 串行化，原子发布删除量、容量结果与错误；LogManager.getLastCapacityResult() 转发最近轮次结果。

### 11.2 多模块发布

继续排除真机、模拟器、ADB、安装/运行示例、真实业务数据、正式签名、远程发布、Git 提交/推送及全局环境修改。Android 编译/R8/Lint 结果不代替 Room 数据库、最低 API 设备或混淆后运行验证。

本轮 POM 修复只选择 `-Offline -Stages Environment,Publish,Consumers,PublicationArtifacts`。离线模式先核对已有固定 Wrapper 分发，直接用已存在的 Gradle 7.5 启动，不自动下载；各消费者使用独立可写缓存，第三方依赖只读取已有 `.gradle/verification-home/caches` 种子，本库排他从本次临时 Maven 仓库取得。缓存或 SDK 缺失即停止，不回退联网。

`PublicationArtifacts` 使用 Publish/Consumers 的本次产物，检查包内许可、完整 POM、`.module` 及 POM 重定向标记缺席、源码包和哈希；原完整 `Artifacts` 阶段继续要求测试、Lint、schema 等完整验收证据。历史 149 项测试与旧三消费者 POM/module 结果不作为当前修改的通过证据；首次离线局部通过及 Android 失败均保留。最终 `20260913-pom-local-final` 四阶段与六消费者通过，核验 66 个当前构建输入源码条目和 121 个 Java 11 类；实际命令、输入指纹与产物哈希见[公开发布说明](公开发布说明.md)。本轮没有重跑完整测试或完整 Lint，Release 构建自带的 lintVital 已执行。

未来远端 `scripts/verify-jitpack-consumer.ps1` 必须另获授权并启用 `AllowRemoteBuild`，针对新完整提交执行 `DefaultMaven`（不设置 `metadataSources`）和 `PomOnly`（`mavenPom()` 加 `ignoreGradleMetadataRedirection()`），共六个独立空缓存消费者。本库只从 JitPack 获取，远端 `.module` 须 HTTP 404、POM 不含重定向标记，源码逐条对应精确提交，并核对依赖图和 Kotlin BOM。离线本地验证不等于远端空缓存验证，新矩阵也不能称为原 ModuleOnly 验收通过。本轮只准备此入口，不调用远程，详见[公开发布说明](公开发布说明.md)。
