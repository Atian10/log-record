## 1. 概述

log-record 是一个跨平台日志记录库，将日志持久化到数据库（Android Room / JDBC SQLite），支持条件查询、聚合统计、多格式导出和自动清理。

**核心能力：**

| 能力 | 说明 |
|------|------|
| 日志写入 | 5 级别（DEBUG~FATAL）+ 自定义类型 + 用户键值对字段 |
| 异步引擎 | 单线程 + 队列 + 批处理；BLOCK 且队列满时业务线程可能等待 |
| 持久化 | 已确认成功提交的记录可跨正常重启保留；内存队列、失败/丢弃/UNKNOWN 记录不保证保存，清理规则仍可删除数据 |
| 查询统计 | 按级别/类型/Tag/关键字/时间/版本/用户字段组合查询 |
| 导出 | JSON / CSV / TXT 三种格式，支持条件筛选导出 |
| 自动清理 | 按天数/容量/数量三维度，定时自动执行 |
| 异常存储 | 异常堆栈独立存表，不影响日志主表 |
| 热更新 | 运行时 CAS 修改 8 项动态配置，无需重启 |

## 3. 接入指南

### 3.1 Android 接入

#### 方式一：按模块使用 Maven 依赖

**第 1 步：添加 JitPack 仓库**

项目根目录 `build.gradle`：

```gradle
allprojects {
    repositories {
        google()
        mavenCentral()
        maven { url 'https://jitpack.io' }
    }
}
```

> 如果项目使用 `settings.gradle` 的 `dependencyResolutionManagement`，改为：
> ```gradle
> dependencyResolutionManagement {
>     repositories {
>         google()
>         mavenCentral()
>         maven { url 'https://jitpack.io' }
>     }
> }
> ```

**第 2 步：添加依赖**

app 模块 `build.gradle`：

```gradle
dependencies {
    implementation 'com.github.Atian10.log-record:log-android:v2.0.0-rc.1'
}
```

> 该标签与其精确提交版本均已通过远端发布和消费验证，可直接按上方坐标接入。验收只覆盖依赖解析、编译、打包及制品，不包括设备、数据库或线上业务运行。Android 接入只声明 `log-android`，不能以聚合坐标同时引入 Android 和 Desktop；后续版本须查看各自验证记录。

三个库采用完整 Maven POM 传递依赖及范围，不发布 Gradle Module Metadata（`.module`），POM 不含其重定向标记。源码以 `sources` classifier 获取，例如 `log-core-v2.0.0-rc.1-sources.jar`。Android 保留 Kotlin BOM 1.8.0 的 POM import，并显式发布 `kotlin-stdlib-jdk7:1.8.0`、`kotlin-stdlib-jdk8:1.8.0` 的运行时依赖，补齐 POM 接入的标准库对齐；通过 Maven 接入时不要求消费方另加 BOM 或强制版本。Java 11 要求通过字节码和独立消费编译检查；本版本远端默认 Maven／强制 POM 两模式均已通过，旧远端元数据错误保留为历史失败。

#### 方式二：本地 Module 依赖

将 `log-android` 和 `log-core` 复制到你的项目，在 `settings.gradle` 中引入：

```gradle
include ':log-core'
include ':log-android'
project(':log-core').projectDir = new File('path/to/log-record/log-core')
project(':log-android').projectDir = new File('path/to/log-record/log-android')
```

app 模块 `build.gradle`：

```gradle
dependencies {
    implementation project(':log-android')
}
```

#### 方式三：AAR 文件依赖（v2.0.0-rc.1）

下载本次已发布的两个文件，保留原文件名，放入 app 模块 `libs/` 目录：

- [log-android-v2.0.0-rc.1.aar](https://jitpack.io/com/github/Atian10/log-record/log-android/v2.0.0-rc.1/log-android-v2.0.0-rc.1.aar)
- [log-core-v2.0.0-rc.1.jar](https://jitpack.io/com/github/Atian10/log-record/log-core/v2.0.0-rc.1/log-core-v2.0.0-rc.1.jar)

```gradle
dependencies {
    implementation files('libs/log-android-v2.0.0-rc.1.aar')
    implementation files('libs/log-core-v2.0.0-rc.1.jar')
    implementation 'com.google.code.gson:gson:2.10.1'
    implementation 'androidx.room:room-runtime:2.5.2'
    implementation 'androidx.annotation:annotation:1.6.0'
    implementation platform('org.jetbrains.kotlin:kotlin-bom:1.8.0')
    runtimeOnly 'org.jetbrains.kotlin:kotlin-stdlib-jdk7:1.8.0'
    runtimeOnly 'org.jetbrains.kotlin:kotlin-stdlib-jdk8:1.8.0'
}
```

> 单个 AAR 不包含 `log-core`，文件依赖也不读取 POM 中的依赖与约束。上例两个库文件均使用 `v2.0.0-rc.1`，其余声明对应已发布 POM 的依赖；Kotlin BOM 和 jdk7/jdk8 的 1.8.0 对齐声明须一并保留。项目仍需配置 `google()` 和 `mavenCentral()` 来解析这些依赖及其传递依赖。若全部改成离线文件，还需备齐传递制品和许可。已完成的独立消费编译采用 Maven 方式，手动文件接入未另行编译验证；优先使用上面的 Maven 依赖。

自行从源码构建可运行 `./gradlew :log-android:assembleRelease :log-core:jar`。未显式指定构建版本时，输出为 `log-android/build/outputs/aar/log-android-release.aar` 和 `log-core/build/libs/log-core-0.0.0-local-validation.jar`，引用时按实际文件名调整；这些本地输出与上面的远端发行文件分别命名。Windows 使用 `./gradlew.bat`。

#### ProGuard / R8 混淆

**无需额外配置**。`log-android` 的 `consumer-rules.pro` 会自动传递到消费方，覆盖 Room 实体类、DAO、Gson TypeToken、枚举等 keep 规则。

#### 初始化

在已注册的 `Application.onCreate()` 中初始化。以下 `MyApp.java` 放在应用 namespace 对应的包内；需要导入 `android.app.Application`、`com.atian10.logrecord.android.AndroidLogInit`、`com.atian10.logrecord.core.config.CleanPolicy`、`com.atian10.logrecord.core.config.LogConfig`。Manifest 的 `.MyApp` 对应此包内的类。

<!-- verification:android-init -->
```java
public class MyApp extends Application {
    @Override
    public void onCreate() {
        super.onCreate();

        AndroidLogInit.init(this, new LogConfig.Builder()
            .versionTag("1.0.0")                     // 业务版本标签
            .consoleEnabled(true)                     // 输出到 Logcat
            .captureMethodLine(true)                  // 捕获调用方法名/行号
            .queueCapacity(4096)                      // 异步队列容量（默认 4096）
            .batchSize(100)                           // 批量写入阈值（默认 100）
            .batchIntervalMillis(1000L)               // 批量写入周期（默认 1 秒）
            .cleanPolicy(CleanPolicy.builder()        // 日志自动清理
                .enable(true)
                .keepDays(7)                          // 保留 7 天
                .maxDbSizeMB(50)                      // 旧容量参数（自动迁移为全库预算；也可改用 databaseMaxSizeMB 显式配置）
                .maxRecordCount(50000)                // 记录上限 5 万条
                .cleanIntervalHours(24)               // 每 24 小时检查
                .build())
            .exceptionCleanPolicy(CleanPolicy.builder()  // 异常自动清理
                .enable(true)
                .keepDays(30)                         // 异常保留 30 天
                .build()));
    }
}
```

在 app 的 `src/main/AndroidManifest.xml` 中合入以下注册属性，保留原有 `<application>` 的其他属性和组件：

<!-- verification:android-manifest -->
```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application android:name=".MyApp" />
</manifest>
```

已有自定义 Application 时，直接在已经注册的类中添加初始化调用，不再注册第二个 Application。仅创建 `MyApp` 类而不注册，不会自动执行其 `onCreate()`。

> ⚠️ `AndroidLogInit.init` 会自动使用 ApplicationContext 构建数据库，无需手动创建 RoomStorage。

## 4. 核心 API

### 4.1 LogManager（全局入口）

所有操作通过 `LogManager.get()` 获取单例。

#### 写入日志

| 方法 | 说明 |
|------|------|
| `d(tag, message)` | DEBUG 级别 |
| `i(tag, message)` | INFO 级别 |
| `w(tag, message)` | WARN 级别 |
| `e(tag, message)` | ERROR 级别 |
| `f(tag, message)` | FATAL 级别 |
| `e(tag, message, throwable)` | ERROR + 异常独立写入 |
| `f(tag, message, throwable)` | FATAL + 异常独立写入 |
| `log(level, type, tag, message)` | 完整参数（自定义类型） |
| `log(level, type, tag, message, userFields)` | 携带用户键值对 |
| `log(level, type, tag, message, throwable)` | 携带异常 |
| `log(level, type, tag, message, userFields, throwable)` | 全参数 |
| `recordException(throwable, tag)` | 仅写异常（不伴随日志） |

```java
// 便捷方法
LogManager.get().i("MainActivity", "页面加载完成");

// 自定义类型 + 用户字段
Map<String, String> fields = new HashMap<>();
fields.put("userId", "12345");
fields.put("orderId", "ORD-001");
LogManager.get().log(LogLevel.INFO, "BUSINESS", "OrderService",
    "订单创建成功", fields);

// 异常独立写入
LogManager.get().e("NetworkService", "请求超时", new SocketTimeoutException());
// 写入 1 条 ERROR 日志 + 1 条异常记录（独立表）
```

#### 查询日志

> ⚠️ **禁止在主线程调用**，否则会触发 ANR。

```java
List<LogRecord> records = LogManager.get().queryLogs(
    LogQuery.builder()
        .level(LogLevel.ERROR)                    // 按级别
        .type(StandardLogType.NETWORK.code())     // 按类型
        .tag("LoginActivity")                     // 按 Tag
        .keyword("失败")                          // 按关键字（模糊匹配 message）
        .fromTime(startTime)                      // 起始时间（毫秒）
        .toTime(endTime)                          // 结束时间（毫秒）
        .versionTag("1.2.3")                      // 按版本标签
        .userField("errorCode", "AUTH_FAIL")      // 按用户字段
        .orderBy(OrderBy.DESC)                    // 排序（默认 DESC）
        .offset(0)                                // 分页偏移
        .limit(100)                               // 每页条数
        .build());
```

#### 聚合统计

```java
LogStatistics stats = LogManager.get().statistics(
    LogQuery.builder()
        .fromTime(today)
        .build());

stats.getTotalCount();        // 总数
stats.getCountByLevel();      // Map<LogLevel, Long> 按级别
stats.getCountByType();       // Map<String, Long> 按类型
stats.getCountByTag();        // Map<String, Long> 按标签
```

#### 查询异常

异常类型按完整类名匹配。以下调用放在后台线程，`startTime`、`endTime` 为业务方传入的毫秒时间边界。

<!-- verification:exception-query -->
```java
List<ExceptionRecord> exceptions = LogManager.get().queryExceptions(

        .tag("LoginActivity")
        .exceptionClass(NullPointerException.class.getName())
        .fromTime(startTime)
        .toTime(endTime)
        .orderBy(OrderBy.DESC)

```

#### 导出日志

Android 使用应用内部目录，不直接写 `/sdcard`。以下语句放在接收 `android.content.Context context` 参数的业务方法中，参数由 Activity 或 Application 提供。需要导入 `java.io.File`、`com.atian10.logrecord.core.LogManager`、`com.atian10.logrecord.core.export.ExportCallback`、`com.atian10.logrecord.core.export.ExportFormat`、`com.atian10.logrecord.core.model.LogLevel`、`com.atian10.logrecord.core.query.LogQuery`。文件位于 `context.getFilesDir()`，无需外部存储权限；示例开启后台线程执行导出。

<!-- verification:android-export -->
```java
String outputPath = new File(context.getFilesDir(), "logs.json").getAbsolutePath();
new Thread(() -> LogManager.get().exportLogs(
    LogQuery.builder().level(LogLevel.ERROR).build(),
    ExportFormat.JSON,
    outputPath,
    new ExportCallback() {
        @Override public void onProgress(int exported, int total) {
            // 后台线程收到进度；更新 UI 时切回主线程。
        }
        @Override public void onSuccess(String filePath, int totalCount) {
            // 完整文件已发布到目标路径。
        }
        @Override public void onFailure(Throwable error, int exportedCount) {
            // 至多一次；保留原目标，清理错误附加在异常中。
        }
    }), "export-logs").start();
```

Desktop 使用同一导出 API，但路径由业务方指定为当前进程可写的文件绝对路径，并事先准备父目录；不使用上述 Android Context。导出仍同步执行，是否调度到后台由业务方决定。

> **导出契约**：
> - 集合一致性：导出开始时捕获已提交数据边界，并发写入/清理不会导致导出文件重复或遗漏；导出进行中清理被推迟。
> - 失败语义：任一必要步骤（count、快照读取/关闭、格式化、写文件/关闭、发布）失败即整体失败，`onFailure` 至多一次；单条格式化失败会终止导出（不跳过后报告成功）。
> - 回调线程：回调在调用导出的线程触发。Android 上导出（含数据库与文件 IO）**禁止在主线程调用**，请在子线程执行。
> - 自定义存储：需实现 `openExportSnapshot` 提供快照适配，否则导出明确失败（不会回退到不可靠的分页方式）。

> - 发布要求：Android 使用 API 21 的 `Os.rename`，Desktop 要求 `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`；不支持原子替换时明确失败。文件系统与 R8 后的实际行为仍需独立验证。
> - 保护范围：仅覆盖本库管理的写入、清理和关闭；原始 DAO/Connection、其他进程改库不在保证范围内。进程异常退出后的临时残留没有自动清理功能。

#### 手动清理

```java
// 清理含数据库删除与全库容量维护，Android 上禁止在主线程调用
LogManager.get().cleanNow(new CleanCallback() {
    @Override
    public void onSuccess(int cleanedCount) {
        // 表级规则清理完成（容量阶段结果见下方说明）
    }
    @Override
    public void onFailure(Throwable error) {
        // 清理失败
    }
});
```

> 配置了容量预算时，`cleanNow` 在表级规则之后执行全库容量维护；
> 只有表级规则完成且容量阶段为 MET（或未启用容量阶段）才调用 `onSuccess`；NOT_MET、POSTPONED、FAILED 均只调用 `onFailure`。
> `cleanNow` 返回值和回调中的数量只含表级删除；容量阶段的已确认删除量、字节数、结局及停止原因通过 `LogManager.get().getLastCapacityResult()` 获取，告警通过 `getLastWarning()` 获取。
> 手动与定时清理串行执行并发布同一轮结果；下一轮未执行容量阶段时，该轮容量结果为 null。

#### 运行时配置更新

```java
LogManager manager = LogManager.get();
LogConfigUpdater updater = manager.getConfigUpdater();

updater.updateVersionTag("2.0.0");              // 修改版本标签
updater.updateConsoleEnabled(false);            // 关闭控制台输出
updater.updateCaptureMethodLine(true);          // 开启方法名捕获
updater.updateCleanPolicy(newPolicy);           // 修改清理策略
manager.refreshCleanPolicies();                // 将当前两表策略同步到 CleanTask
updater.updateExportEncoding(ExportEncoding.GBK); // 修改导出编码
```

> 配置对象通过 CAS 原子替换，无需重启引擎。修改 `cleanPolicy` / `exceptionCleanPolicy` 后须对同一管理器调用 `refreshCleanPolicies()`，CleanTask 才采用新策略；从禁用改为启用的调度启动也发生在刷新时。

#### 控制台与格式化（未发布修复）

`LogManager` 是默认平台接入中 `consoleEnabled` 的唯一控制者，每次写入捕获同一份配置快照。无论初始化为 true 还是 false，均可调用 `updateConsoleEnabled(false)` 关闭，再调用 `updateConsoleEnabled(true)` 开启；后续记录采用更新后的配置，不需要重新初始化。

平台入口通过 `LogManager.init(config, strategy)` 注入核心接口 `IConsoleOutput`，该接口分别接收 `print(LogRecord, IFormatter)` 和 `print(ExceptionRecord, IFormatter)`。默认 Android／Desktop 接入直接使用数据库存储，不再默认套用 `LogcatStorage`／`ConsoleStorage` 装饰器，也不强制把核心开关设成 false。

控制台策略保留平台的 tag、级别和 FATAL 映射；Desktop 的 WARN／ERROR／FATAL 及异常走 stderr，DEBUG／INFO 走 stdout。formatter 非空时按 `ExportFormat.TXT` 格式化，更新后作用于后续控制台分发及下一次导出；formatter 设为 null 时，控制台恢复各平台默认文本，导出按自己的默认格式化规则处理。

控制台在记录提交给引擎后、调用线程中同步输出，因此慢 formatter 或输出策略会延长调用耗时。输出成功不代表数据库已保存，落盘仍依据 flush 结果。格式化或输出抛出普通 `RuntimeException` 时记录内部 warning，不以默认文本回退重复输出；它不改写已经提交给引擎的记录结果。关闭开始后跳过新的控制台分发，关闭前已通过 RUNNING 检查的在途分发可以完成，关闭流程不等待它们，也不保证返回后这些调用不会继续物理输出。

旧 `LogcatStorage`／`ConsoleStorage` 构造器仍可单独使用，保留自身固定开关语义。业务方若主动将旧装饰器与核心控制台策略一起组合，即选择了额外输出通道，可能重复输出；这不是默认平台接入方式。

```java
LogStatus status = LogManager.get().getStatus();
// State: NORMAL / DEGRADED / ERROR / SHUTDOWN
// warningCount: 告警计数
// message: 状态描述
```

#### 落盘与关闭

```java
// flush：等待调用时刻已接收的记录全部到达终态（保存/失败/丢弃/结果未知）
LogManager.get().flush();                    // 兼容入口：默认 5 秒
FlushResult r = LogManager.get().flush(2000L); // 带超时，返回等待结果
// r.isAllPersisted(): 整个目标范围全部确认保存，无失败/丢弃/未知
// getSaved/getFailed/getDropped/getUnknown：本次等待期间增量
// getTargetSaved/getTargetFailed/getTargetDropped/getTargetUnknown：目标累计（含历史）
// getPending：返回时目标范围内仍未终结的条数

// shutdown：停止新准入和清理调度，后台等待引擎、清理及活动操作后关闭数据库
LogManager manager = LogManager.get();
ShutdownResult s = manager.shutdown(3000L);         // 带超时，返回关闭结果
// 或使用 manager.shutdown() 兼容入口（默认 5 秒），二者按需选择
// s.isFullyTerminated(): 引擎、清理和活动操作已退出，配置的数据库关闭已完成
// 超时时后台继续收尾；重复关闭幂等，旧实例关闭不会影响新实例
```

> **线程提示**：`flush(long)` 与 `shutdown(long)` 是阻塞等待，Android 上请在子线程调用；
> `shutdown(0)` 不等待；正时限覆盖整个关闭调用。超时后同一管理器的后台收尾者继续等待活动操作与快照，然后关闭所属平台数据库；重复调用可取得更新后的结果。直接调用管理器与平台关闭入口共用这一路径。
> 快照必须在创建线程读取和关闭；快照未释放会延后资源关闭。关闭开始后拒绝新的数据库业务入口，已经准入的操作可以完成。

### 4.4 清理策略

维护按主文件及存在的 WAL、SHM、journal 文件长度之和度量。未知或失败度量以 `-1` 表示，不视为零；它不是文件系统分配簇占用，也不包含导出临时文件。

两表按 `(timestamp, 固定表顺序 log→exception, id)` 合并选取具体 ID，每批最多 500 条，同一事务提交后回收并重新度量。checkpoint 忙碌/失败、回收失败、空间不足或无物理进展时停止容量删除；协调器实例随后仅做无删除恢复检查，恢复轮次不继续删除。无进展状态需观察到物理体积下降或已达标才解除。该保护不跨实例重建/进程重启持久化，也不限制之后追加写入形成硬配额；独立的天数和数量规则仍按配置执行。

新旧 MB 参数均先做非负与乘法溢出检查，即使旧策略禁用也拒绝非法值；1 MB = 1024 × 1024 字节。


清理分两个层级：

**表级规则**（每张表独立执行，互不影响）：

```java
CleanPolicy policy = CleanPolicy.builder()
    .enable(true)                // 是否启用（默认 false）
    .keepDays(7)                // 保留天数（0 = 不按天清理）
    .maxRecordCount(50000)      // 记录数上限（0 = 不限）
    .cleanIntervalHours(24)     // 检查周期（小时，默认 24）
    .build();
```

**全库容量预算**（数据库级，按整个数据库磁盘占用统一限制）：

```java
LogConfig.builder()
    .databaseMaxSizeMB(100L)    // 全库预算：正数=预算；0=显式禁用；不设置=按旧值迁移
    ...                         // 度量口径：主文件 + -wal + -shm + -journal 长度和
    .build();
```

**旧 `maxDbSizeMB` 参数迁移规则**（在 `build()` 校验，冲突抛 `IllegalArgumentException`）：

| 配置情形 | 处理 |
| --- | --- |
| 未设置 `databaseMaxSizeMB`，启用策略的旧容量值相同（或仅一个有效值） | 自动映射为全库预算，参与表 = 启用且有旧正容量值的表 |
| 未设置，启用策略的旧正容量值不同 | 配置冲突，拒绝构建 |
| 显式设置新预算 + 启用策略存在旧正值 | 必须一致，否则冲突；显式预算参与表 = 全部启用策略的表 |
| 显式 `0`（禁用）+ 启用策略存在旧正值 | 冲突；需先清除旧值 |
| 没有任何有效容量预算 | 不执行容量驱动删除，表级过期/数量清理照常 |

> 容量超限时按参与表中**全局最旧记录**逐批删除（含 WAL checkpoint 与空闲页回收），
> 达标即停；keepDays 是过期删除条件，不是容量超限时的最低保留承诺。
> 禁用清理策略的表始终受保护；无可删数据导致无法达标时记录告警（`getLastWarning()`），
> 不虚报成功。跨进程改库或外部直接写库不在一致性保证内。

仓库示例的 Manifest 已注册 `SampleApp`。复制到业务工程时，也要将对应类注册到 `<application android:name="...">`；已有 Application 时合并初始化调用。

```java
// Application 初始化
public class SampleApp extends Application {
    @Override
    public void onCreate() {
        super.onCreate();
        AndroidLogInit.init(this, new LogConfig.Builder()
            .versionTag("android-sample-1.0.0")
            .consoleEnabled(true)
            .captureMethodLine(true)
            .queueCapacity(2048)
            .batchSize(100)
            .batchIntervalMillis(1000L)
            .cleanPolicy(CleanPolicy.builder()
                .enable(true).keepDays(7).maxDbSizeMB(100)
                .maxRecordCount(50000).cleanIntervalHours(24).build())
            .exceptionCleanPolicy(CleanPolicy.builder()
                .enable(true).keepDays(30).build()));
    }
}

// Activity 查询（子线程）
new Thread(() -> {
    List<LogRecord> records = LogManager.get().queryLogs(
        LogQuery.builder()
            .level(LogLevel.ERROR)
            .fromTime(System.currentTimeMillis() - 3600_000L)
            .orderBy(OrderBy.DESC)
            .limit(20)
            .build());
    runOnUiThread(() -> showResult(records));
}, "query-error-logs").start();
```

## 6. 常见问题

### Q1：日志写在哪个文件？

**Android**：`/data/data/{包名}/databases/log_record.db`（由 Room 管理）
**桌面/服务器**：`DesktopLogInit.init(dbPath, ...)` 指定的路径

### Q2：日志写入会卡 UI 吗？

数据库写入由异步引擎执行。配置 BLOCK 策略且队列满时，入队最多等待 1 秒；未发布修复中的控制台策略还会在提交引擎后于调用线程同步格式化和输出，因此慢 formatter／输出也会延长调用耗时，不能保证业务线程完全不等待。

### Q3：查询会卡 UI 吗？

**会**。查询是同步数据库操作，**禁止在 Android 主线程调用**。请在子线程执行，通过 `runOnUiThread()` 切回主线程更新 UI。

> 库会在检测到主线程调用时输出警告日志：`⚠️ query() called on main thread!`

### Q4：release 混淆后还能用吗？

2026-09-12 的历史验证（收录于提交 `76497adcfd40aa2c0720464197b64b833f55a259`）完成了示例 Release/R8 构建，并核对 AAR 中的消费规则与 R8 实际配置、mapping 产物。它证明该次构建与规则传递通过；本轮新结果另记于[公开发布说明](公开发布说明.md)。Android 上 Room、导出反射路径及混淆后的实际行为未执行运行验证。

### Q5：数据库多大？会无限增长吗？

配置清理后按策略尝试回收。`keepDays`（过期）与 `maxRecordCount`（数量）是表级规则，
`databaseMaxSizeMB` 是一次容量维护的目标；旧 `maxDbSizeMB` 按迁移规则折算。维护可能未达标，之后写入也可能继续增长，不构成持续硬上限。

### Q6：支持多进程吗？

不支持。同一 SQLite 文件不支持多进程并发访问。多进程场景请每个进程使用独立的数据库文件。

### Q7：如何上报日志到服务器？

库不实现网络上报（设计决策）。业务方通过 `queryLogs()` 查询后自行上传：

```java
List<LogRecord> errorLogs = LogManager.get().queryLogs(
    LogQuery.builder()
        .level(LogLevel.ERROR)
        .fromTime(lastReportTime)
        .build());
uploadToServer(errorLogs);  // 业务自行实现
```

### Q8：如何修改队列容量等静态配置？

静态配置（queueCapacity/batchSize/batchIntervalMillis/queueFullPolicy）初始化后不可修改。如需修改：

```java
LogManager previous = LogManager.get();
ShutdownResult result = previous.shutdown(3000L); // 在后台线程调用
if (result.isFullyTerminated()) {
    AndroidLogInit.init(context, newConfigBuilder);
}
// 超时则保留 previous；确认 previous.isTerminated() 后才可重新初始化。
```

> 通过 `LogConfigUpdater.set()` 修改静态配置会抛 `IllegalArgumentException`。

### Q9：捕获的方法名/行号不正确？

确保初始化时开启 `captureMethodLine(true)`。便捷方法（`d/i/w/e/f`）与 `log()` 均已修正栈帧定位（v1.5），指向业务调用者本身。

### Q10：导出的文件在哪里？

导出路径由 `exportLogs()` 的 `outputPath` 参数指定。本文 Android 接入示例使用 `new File(context.getFilesDir(), "logs.json").getAbsolutePath()`，即应用内部文件目录，无需外部存储权限；`context` 由 Activity 或 Application 提供，导出在后台执行。仓库交互示例若选择应用缓存目录，其路径以该示例显示结果为准。Desktop 则由业务方选择进程可写的文件绝对路径，并准备父目录。

### Q11：修改控制台开关或 formatter 后何时生效？

当前未发布修复让下一次写入使用新的配置快照；初始 false 也可以切为 true。formatter 非空时控制台使用 TXT，null 恢复平台默认文本。`v2.0.0-rc.1` 仍存在本次针对的控制台开关与 formatter 传递问题，不能用旧坐标取得本地修复，详见 [Unreleased](../CHANGELOG.md#unreleased)。

## 7. 注意事项

| 注意项 | 说明 |
|--------|------|
| 🔴 查询/导出/清理/flush 禁止主线程 | 涉及数据库与文件 IO 或阻塞等待的操作均在子线程执行（示例见 `log-sample-android` 的后台执行器） |
| 🟡 不支持多进程 | 同一 SQLite 文件不支持多进程并发访问 |
| 🟡 不支持网络上报 | 库只负责本地存储，业务方需自行 query + upload |
| 🟡 不支持级别过滤 | 所有级别强制写入，不支持 `setLevel(WARN)` 只收 WARN 以上 |
| 🟡 compileSdk / targetSdk 33 | 是当前构建基线，不证明任何应用商店的上架资格；业务应用需另行核对目标商店当时的政策及自身配置 |
| 🟡 Activity onDestroy | 需要收尾时在后台线程调用 `flush(long)`（阻塞等待，勿在主线程）；库关闭由平台层负责 |
| 🟡 数据库位置 | Android 自动使用 `context.getDatabasePath("log_record.db")` |
