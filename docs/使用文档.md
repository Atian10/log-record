## 1. 概述

log-record 是一个跨平台日志记录库，将日志持久化到数据库（Android Room / JDBC SQLite），支持条件查询、聚合统计、多格式导出和自动清理。

**核心能力：**

| 能力 | 说明 |
|------|------|
| 日志写入 | 5 级别（DEBUG~FATAL）+ 自定义类型 + 用户键值对字段 |
| 异步引擎 | 单线程 + 队列 + 批处理，不阻塞业务线程 |
| 持久化 | 自动存入 SQLite 数据库，重启不丢失 |
| 查询统计 | 按级别/类型/Tag/关键字/时间/版本/用户字段组合查询 |
| 导出 | JSON / CSV / TXT 三种格式，支持条件筛选导出 |
| 自动清理 | 按天数/容量/数量三维度，定时自动执行 |
| 异常存储 | 异常堆栈独立存表，不影响日志主表 |
| 热更新 | 运行时 CAS 修改 8 项动态配置，无需重启 |

## 3. 接入指南

### 3.1 Android 接入

#### 方式一：JitPack 远程依赖（推荐）

**第 1 步：添加 JitPack 仓库**

项目根目录 `build.gradle`：

```gradle
allprojects {
    repositories {
        google()
        mavenCentral()
        maven { url 'https://jitpack.io' }
    }
}
```

> 如果项目使用 `settings.gradle` 的 `dependencyResolutionManagement`，改为：
> ```gradle
> dependencyResolutionManagement {
>     repositories {
>         google()
>         mavenCentral()
>         maven { url 'https://jitpack.io' }
>     }
> }
> ```

**第 2 步：添加依赖**

app 模块 `build.gradle`：

```gradle
dependencies {
    implementation 'com.github.Atian10:log-record:v1.5'
}
```

> 访问 [JitPack](https://jitpack.io/com/github/Atian10/log-record) 查看可用版本。首次拉取会触发 JitPack 构建，约 2-3 分钟。

#### 方式二：本地 Module 依赖

将 `log-android` 和 `log-core` 复制到你的项目，在 `settings.gradle` 中引入：

```gradle
include ':log-core'
include ':log-android'
project(':log-core').projectDir = new File('path/to/log-record/log-core')
project(':log-android').projectDir = new File('path/to/log-record/log-android')
```

app 模块 `build.gradle`：

```gradle
dependencies {
    implementation project(':log-android')
}
```

#### 方式三：AAR 文件依赖

```bash
# 编译产出 AAR
gradle :log-android:assembleRelease
# 产出路径：log-android/build/outputs/aar/log-android-release.aar
```

将 AAR 放入 app 模块 `libs/` 目录：

```gradle
dependencies {
    implementation files('libs/log-android-release.aar')
}
```

> ⚠️ AAR 方式需手动处理传递依赖（Gson、Room、AndroidX Annotation），建议优先使用 JitPack。

#### ProGuard / R8 混淆

**无需额外配置**。`log-android` 的 `consumer-rules.pro` 会自动传递到消费方，覆盖 Room 实体类、DAO、Gson TypeToken、枚举等 keep 规则。

#### 初始化

在 `Application.onCreate()` 中初始化：

```java
public class MyApp extends Application {
    @Override
    public void onCreate() {
        super.onCreate();

        AndroidLogInit.init(this, new LogConfig.Builder()
            .versionTag(BuildConfig.VERSION_NAME)    // 版本标签
            .consoleEnabled(true)                     // 输出到 Logcat
            .captureMethodLine(true)                  // 捕获调用方法名/行号
            .queueCapacity(4096)                      // 异步队列容量（默认 4096）
            .batchSize(100)                           // 批量写入阈值（默认 100）
            .batchIntervalMillis(1000L)               // 批量写入周期（默认 1 秒）
            .cleanPolicy(CleanPolicy.builder()        // 日志自动清理
                .enable(true)
                .keepDays(7)                          // 保留 7 天
                .maxDbSizeMB(50)                      // 旧容量参数（自动迁移为全库预算；也可改用 databaseMaxSizeMB 显式配置）
                .maxRecordCount(50000)                // 记录上限 5 万条
                .cleanIntervalHours(24)               // 每 24 小时检查
                .build())
            .exceptionCleanPolicy(CleanPolicy.builder()  // 异常自动清理
                .enable(true)
                .keepDays(30)                         // 异常保留 30 天
                .build())
            .build());
    }
}
```

> ⚠️ `AndroidLogInit.init` 会自动使用 ApplicationContext 构建数据库，无需手动创建 RoomStorage。

## 4. 核心 API

### 4.1 LogManager（全局入口）

所有操作通过 `LogManager.get()` 获取单例。

#### 写入日志

| 方法 | 说明 |
|------|------|
| `d(tag, message)` | DEBUG 级别 |
| `i(tag, message)` | INFO 级别 |
| `w(tag, message)` | WARN 级别 |
| `e(tag, message)` | ERROR 级别 |
| `f(tag, message)` | FATAL 级别 |
| `e(tag, message, throwable)` | ERROR + 异常独立写入 |
| `f(tag, message, throwable)` | FATAL + 异常独立写入 |
| `log(level, type, tag, message)` | 完整参数（自定义类型） |
| `log(level, type, tag, message, userFields)` | 携带用户键值对 |
| `log(level, type, tag, message, throwable)` | 携带异常 |
| `log(level, type, tag, message, userFields, throwable)` | 全参数 |
| `recordException(throwable, tag)` | 仅写异常（不伴随日志） |

```java
// 便捷方法
LogManager.get().i("MainActivity", "页面加载完成");

// 自定义类型 + 用户字段
Map<String, String> fields = new HashMap<>();
fields.put("userId", "12345");
fields.put("orderId", "ORD-001");
LogManager.get().log(LogLevel.INFO, "BUSINESS", "OrderService",
    "订单创建成功", fields);

// 异常独立写入
LogManager.get().e("NetworkService", "请求超时", new SocketTimeoutException());
// 写入 1 条 ERROR 日志 + 1 条异常记录（独立表）
```

#### 查询日志

> ⚠️ **禁止在主线程调用**，否则会触发 ANR。

```java
List<LogRecord> records = LogManager.get().queryLogs(
    LogQuery.builder()
        .level(LogLevel.ERROR)                    // 按级别
        .type(StandardLogType.NETWORK.code())     // 按类型
        .tag("LoginActivity")                     // 按 Tag
        .keyword("失败")                          // 按关键字（模糊匹配 message）
        .fromTime(startTime)                      // 起始时间（毫秒）
        .toTime(endTime)                          // 结束时间（毫秒）
        .versionTag("1.2.3")                      // 按版本标签
        .userField("errorCode", "AUTH_FAIL")      // 按用户字段
        .orderBy(OrderBy.DESC)                    // 排序（默认 DESC）
        .offset(0)                                // 分页偏移
        .limit(100)                               // 每页条数
        .build());
```

#### 聚合统计

```java
LogStatistics stats = LogManager.get().statistics(
    LogQuery.builder()
        .fromTime(today)
        .build());

stats.getTotalCount();        // 总数
stats.getCountByLevel();      // Map<LogLevel, Long> 按级别
stats.getCountByType();       // Map<String, Long> 按类型
stats.getCountByTag();        // Map<String, Long> 按标签
```

#### 查询异常

```java
List<ExceptionRecord> exceptions = LogManager.get().queryExceptions(
    ExceptionQuery.builder()
        .tag("LoginActivity")
        .exceptionClass("NullPointerException")
        .fromTime(startTime)
        .toTime(endTime)
        .orderBy(OrderBy.DESC)
        .limit(10)
        .build());
```

#### 导出日志

```java
LogManager.get().exportLogs(
    LogQuery.builder()                // 查询条件（空 = 全部）
        .level(LogLevel.ERROR)
        .build(),
    ExportFormat.JSON,                // 格式：JSON / CSV / TXT
    "/sdcard/logs.json",              // 输出路径
    new ExportCallback() {
        @Override
        public void onProgress(int exported, int total) {
            // 导出进度
        }
        @Override
        public void onSuccess(String filePath, int totalCount) {
            // 导出成功（文件已完整发布到目标路径后触发）
        }
        @Override
        public void onFailure(Throwable error, int exportedCount) {
            // 导出失败（至多一次；保留原目标，清理错误附加在异常中）
        }
    });
```

> **导出契约**：
> - 集合一致性：导出开始时捕获已提交数据边界，并发写入/清理不会导致导出文件重复或遗漏；导出进行中清理被推迟。
> - 失败语义：任一必要步骤（count、快照读取/关闭、格式化、写文件/关闭、发布）失败即整体失败，`onFailure` 至多一次；单条格式化失败会终止导出（不跳过后报告成功）。
> - 回调线程：回调在调用导出的线程触发。Android 上导出（含数据库与文件 IO）**禁止在主线程调用**，请在子线程执行。
> - 自定义存储：需实现 `openExportSnapshot` 提供快照适配，否则导出明确失败（不会回退到不可靠的分页方式）。

> - 发布要求：Android 使用 API 21 的 `Os.rename`，Desktop 要求 `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`；不支持原子替换时明确失败。文件系统与 R8 后的实际行为仍需独立验证。
> - 保护范围：仅覆盖本库管理的写入、清理和关闭；原始 DAO/Connection、其他进程改库不在保证范围内。进程异常退出后的临时残留没有自动清理功能。

#### 手动清理

```java
// 清理含数据库删除与全库容量维护，Android 上禁止在主线程调用
LogManager.get().cleanNow(new CleanCallback() {
    @Override
    public void onSuccess(int cleanedCount) {
        // 表级规则清理完成（容量阶段结果见下方说明）
    }
    @Override
    public void onFailure(Throwable error) {
        // 清理失败
    }
});
```

> 配置了容量预算时，`cleanNow` 在表级规则之后执行全库容量维护；
> 只有表级规则完成且容量阶段为 MET（或未启用容量阶段）才调用 `onSuccess`；NOT_MET、POSTPONED、FAILED 均只调用 `onFailure`。
> `cleanNow` 返回值和回调中的数量只含表级删除；容量阶段的已确认删除量、字节数、结局及停止原因通过 `LogManager.get().getLastCapacityResult()` 获取，告警通过 `getLastWarning()` 获取。
> 手动与定时清理串行执行并发布同一轮结果；下一轮未执行容量阶段时，该轮容量结果为 null。

#### 运行时配置更新

```java
LogConfigUpdater updater = LogManager.get().getConfigUpdater();

updater.updateVersionTag("2.0.0");              // 修改版本标签
updater.updateConsoleEnabled(false);            // 关闭控制台输出
updater.updateCaptureMethodLine(true);          // 开启方法名捕获
updater.updateCleanPolicy(newPolicy);           // 修改清理策略
updater.updateExportEncoding(ExportEncoding.GBK); // 修改导出编码
```

> 配置变更通过 CAS 原子替换生效，线程安全，无需重启引擎。

#### 状态查询

```java
LogStatus status = LogManager.get().getStatus();
// State: NORMAL / DEGRADED / ERROR / SHUTDOWN
// warningCount: 告警计数
// message: 状态描述
```

#### 落盘与关闭

```java
// flush：等待调用时刻已接收的记录全部到达终态（保存/失败/丢弃/结果未知）
LogManager.get().flush();                    // 兼容入口：默认 5 秒
FlushResult r = LogManager.get().flush(2000L); // 带超时，返回等待结果
// r.isAllPersisted(): 整个目标范围全部确认保存，无失败/丢弃/未知
// getSaved/getFailed/getDropped/getUnknown：本次等待期间增量
// getTargetSaved/getTargetFailed/getTargetDropped/getTargetUnknown：目标累计（含历史）
// getPending：返回时目标范围内仍未终结的条数

// shutdown：停止接收 → 停止清理并等待清理线程退出 → 等待引擎排空
LogManager.get().shutdown();                       // 兼容入口：默认 5 秒
ShutdownResult s = LogManager.get().shutdown(3000L); // 带超时，返回关闭结果
// s.isFullyTerminated(): 引擎、清理和活动操作已退出，配置的数据库关闭已完成
// 超时时后台继续收尾；重复关闭幂等，旧实例关闭不会影响新实例
```

> **线程提示**：`flush(long)` 与 `shutdown(long)` 是阻塞等待，Android 上请在子线程调用；
> `shutdown(0)` 不等待；正时限覆盖整个关闭调用。超时后同一管理器的后台收尾者继续等待活动操作与快照，然后关闭所属平台数据库；重复调用可取得更新后的结果。直接调用管理器与平台关闭入口共用这一路径。
> 快照必须在创建线程读取和关闭；快照未释放会延后资源关闭。关闭开始后拒绝新的数据库业务入口，已经准入的操作可以完成。

### 4.2 日志级别

| 级别 | 枚举值 | 数值 | 说明 |
|------|--------|------|------|
| DEBUG | `LogLevel.DEBUG` | 1 | 调试信息 |
| INFO | `LogLevel.INFO` | 2 | 普通信息 |
| WARN | `LogLevel.WARN` | 3 | 警告 |
| ERROR | `LogLevel.ERROR` | 4 | 错误 |
| FATAL | `LogLevel.FATAL` | 5 | 致命错误 |

> 所有级别强制写入，不支持级别门槛过滤。

### 4.3 日志类型

预设类型（`StandardLogType`）：

| 类型 | 代码 |
|------|------|
| NETWORK | `"NETWORK"` |
| UI | `"UI"` |
| DATABASE | `"DB"` |
| BUSINESS | `"BUSINESS"` |
| SYSTEM | `"SYSTEM"` |

自定义类型直接传字符串即可，无需注册：

```java
LogManager.get().log(LogLevel.INFO, "PAYMENT", "PaymentService", "支付成功");
```

### 4.4 清理策略

维护按主文件及存在的 WAL、SHM、journal 文件长度之和度量。未知或失败度量以 `-1` 表示，不视为零；它不是文件系统分配簇占用，也不包含导出临时文件。

两表按 `(timestamp, 固定表顺序 log→exception, id)` 合并选取具体 ID，每批最多 500 条，同一事务提交后回收并重新度量。checkpoint 忙碌/失败、回收失败、空间不足或无物理进展时停止容量删除；协调器实例随后仅做无删除恢复检查，恢复轮次不继续删除。无进展状态需观察到物理体积下降或已达标才解除。该保护不跨实例重建/进程重启持久化，也不限制之后追加写入形成硬配额；独立的天数和数量规则仍按配置执行。

新旧 MB 参数均先做非负与乘法溢出检查，即使旧策略禁用也拒绝非法值；1 MB = 1024 × 1024 字节。


清理分两个层级：

**表级规则**（每张表独立执行，互不影响）：

```java
CleanPolicy policy = CleanPolicy.builder()
    .enable(true)                // 是否启用（默认 false）
    .keepDays(7)                // 保留天数（0 = 不按天清理）
    .maxRecordCount(50000)      // 记录数上限（0 = 不限）
    .cleanIntervalHours(24)     // 检查周期（小时，默认 24）
    .build();
```

**全库容量预算**（数据库级，按整个数据库磁盘占用统一限制）：

```java
LogConfig.builder()
    .databaseMaxSizeMB(100L)    // 全库预算：正数=预算；0=显式禁用；不设置=按旧值迁移
    ...                         // 度量口径：主文件 + -wal + -shm + -journal 长度和
    .build();
```

**旧 `maxDbSizeMB` 参数迁移规则**（在 `build()` 校验，冲突抛 `IllegalArgumentException`）：

| 配置情形 | 处理 |
| --- | --- |
| 未设置 `databaseMaxSizeMB`，启用策略的旧容量值相同（或仅一个有效值） | 自动映射为全库预算，参与表 = 启用且有旧正容量值的表 |
| 未设置，启用策略的旧正容量值不同 | 配置冲突，拒绝构建 |
| 显式设置新预算 + 启用策略存在旧正值 | 必须一致，否则冲突；显式预算参与表 = 全部启用策略的表 |
| 显式 `0`（禁用）+ 启用策略存在旧正值 | 冲突；需先清除旧值 |
| 没有任何有效容量预算 | 不执行容量驱动删除，表级过期/数量清理照常 |

> 容量超限时按参与表中**全局最旧记录**逐批删除（含 WAL checkpoint 与空闲页回收），
> 达标即停；keepDays 是过期删除条件，不是容量超限时的最低保留承诺。
> 禁用清理策略的表始终受保护；无可删数据导致无法达标时记录告警（`getLastWarning()`），
> 不虚报成功。跨进程改库或外部直接写库不在一致性保证内。

## 6. 常见问题

### Q1：日志写在哪个文件？

**Android**：`/data/data/{包名}/databases/log_record.db`（由 Room 管理）
**桌面/服务器**：`DesktopLogInit.init(dbPath, ...)` 指定的路径

### Q2：日志写入会卡 UI 吗？

数据库写入由异步引擎执行，业务线程通常只负责构造记录和入队；配置 BLOCK 策略且队列满时，入队最多等待 1 秒，不能保证业务线程完全不等待。

### Q3：查询会卡 UI 吗？

**会**。查询是同步数据库操作，**禁止在 Android 主线程调用**。请在子线程执行，通过 `runOnUiThread()` 切回主线程更新 UI。

> 库会在检测到主线程调用时输出警告日志：`⚠️ query() called on main thread!`

### Q4：release 混淆后还能用吗？

`consumer-rules.pro` 提供 Room、Gson 等规则；本轮未执行 release/R8 构建或运行验证，新增导出反射路径在混淆后的可用性仍需另行验证。

### Q5：数据库多大？会无限增长吗？

配置清理后按策略尝试回收。`keepDays`（过期）与 `maxRecordCount`（数量）是表级规则，
`databaseMaxSizeMB` 是一次容量维护的目标；旧 `maxDbSizeMB` 按迁移规则折算。维护可能未达标，之后写入也可能继续增长，不构成持续硬上限。

### Q6：支持多进程吗？

不支持。同一 SQLite 文件不支持多进程并发访问。多进程场景请每个进程使用独立的数据库文件。

### Q7：如何上报日志到服务器？

库不实现网络上报（设计决策）。业务方通过 `queryLogs()` 查询后自行上传：

```java
List<LogRecord> errorLogs = LogManager.get().queryLogs(
    LogQuery.builder()
        .level(LogLevel.ERROR)
        .fromTime(lastReportTime)
        .build());
uploadToServer(errorLogs);  // 业务自行实现
```

### Q8：如何修改队列容量等静态配置？

静态配置（queueCapacity/batchSize/batchIntervalMillis/queueFullPolicy）初始化后不可修改。如需修改：

```java
LogManager previous = LogManager.get();
ShutdownResult result = previous.shutdown(3000L); // 在后台线程调用
if (result.isFullyTerminated()) {
    AndroidLogInit.init(context, newConfigBuilder);
}
// 超时则保留 previous；确认 previous.isTerminated() 后才可重新初始化。
```

> 通过 `LogConfigUpdater.set()` 修改静态配置会抛 `IllegalArgumentException`。

### Q9：捕获的方法名/行号不正确？

确保初始化时开启 `captureMethodLine(true)`。便捷方法（`d/i/w/e/f`）与 `log()` 均已修正栈帧定位（v1.5），指向业务调用者本身。

### Q10：导出的文件在哪里？

导出路径由 `exportLogs()` 的 `outputPath` 参数指定。Android 示例导出到 `getExternalCacheDir()`（无需存储权限）。

## 7. 注意事项

| 注意项 | 说明 |
|--------|------|
| 🔴 查询/导出/清理/flush 禁止主线程 | 涉及数据库与文件 IO 或阻塞等待的操作均在子线程执行（示例见 `log-sample-android` 的后台执行器） |
| 🟡 不支持多进程 | 同一 SQLite 文件不支持多进程并发访问 |
| 🟡 不支持网络上报 | 库只负责本地存储，业务方需自行 query + upload |
| 🟡 不支持级别过滤 | 所有级别强制写入，不支持 `setLevel(WARN)` 只收 WARN 以上 |
| 🟡 compileSdk 33 | 可用于国内应用商店；上 Google Play 需升级至 compileSdk 35+ |
| 🟡 Activity onDestroy | 需要收尾时在后台线程调用 `flush(long)`（阻塞等待，勿在主线程）；库关闭由平台层负责 |
| 🟡 数据库位置 | Android 自动使用 `context.getDatabasePath("log_record.db")` |
