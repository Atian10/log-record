## P3：使用契约与版本策略

- `exportLogs` 和 `exportExceptions` 同步执行，回调在调用线程触发。Android 业务方负责在后台执行数据库和文件操作。
- 配置 CAS 更新后，修改清理策略还需对同一管理器调用 `refreshCleanPolicies()`，使 CleanTask 采用新的两表策略。
- 只有已确认成功提交的记录才有跨正常重启保留的依据；内存队列、失败、丢弃或 UNKNOWN 不等于已落盘。正常清理、业务删除及底层存储故障仍可能影响保留，库不提供无限保留承诺。
- 直接引用 AAR 不会读取 POM/module。必须另备同版本 core JAR，补齐 Gson、Room、AndroidX Annotation 和 Kotlin BOM 1.8.0，并解析其传递依赖；优先使用 Module 或 Maven 元数据接入。
- compileSdk/targetSdk 33 是当前构建基线，不表示任何应用商店的上架资格。本轮不升级 SDK，也不作商店政策验收。

[CHANGELOG](../CHANGELOG.md) 使用 `Unreleased`。候选 `v2.0.0-rc.1` 考虑当前 Java 11 要求与失败、关闭等语义变化，只有将来完成发布步骤后才能写为已发布版本。业务日志的 `versionTag` 字段与库的 Maven/Git 版本无关。

## P5：未来另行授权的 JitPack 验证

入口是 `scripts/verify-jitpack-consumer.ps1`，参数为 `Version`、`ExpectedCommit`、`JavaHome`、`SdkDirectory`、`RunId`、`AllowRemoteBuild`。未显式启用 `AllowRemoteBuild` 时应立即拒绝并且不联网；显式开关还必须与当次有效远程授权一致。本轮连拒绝路径也不调用，不访问本项目 JitPack URL/API。

脚本自动检查远程日志中的提交 SHA/版本及构建结果、包非空及 Java 源条目存在、发布元数据、许可和下载原始包的 SHA-256，并执行下述消费者矩阵。它不自动逐项比对源码包内容与本地精确提交，也不自动创建、推送或解析确认候选标签；这些列为发布前/后的人工核对项，不能仅凭脚本成功省略。

获得未来授权后的顺序：

1. **发布前人工核对**：固定完整源码提交 SHA，确认工作区及发布输入与目标提交一致并记录源文件指纹。然后首先用精确提交版本运行脚本验收远程构建及消费，记录远程实际构建提交；不能只接受 HTTP 成功或缓存已有包。
2. **脚本检查与发布后人工复核**：脚本获取远程构建日志、模块坐标、版本、POM/module、三个库 JAR/AAR 与 sources，检查既定元数据并记录下载字节的 SHA-256。随后人工将源码包条目内容逐项与本地精确提交对应，区分源文件内容哈希和整个压缩包哈希；生成文件单列来源。当前脚本不自动完成这项源码内容对应检查。
3. 用两种元数据模式各跑三个消费者，共六个独立验收单元：模式 A 允许 Gradle module metadata；模式 B 仅使用 Maven POM，并禁用重定向到 Gradle module metadata。两种模式都要验证传递依赖与 Kotlin BOM。
4. 每个单元使用独立工程、独立且初始为空的 Gradle 缓存。本库 group 的解析源排他限定为 JitPack；其他依赖按需使用 Google/Maven Central，不得让本库从这些仓库、`mavenLocal`、本地测试仓库、`flatDir`、复合构建或已有缓存回退取得。保存实际来源和依赖图。
5. **标签前后人工核对**：精确提交的全部验收通过后，才在另行授权的 Git/发布步骤创建并推送指向同一提交的候选标签，人工确认标签解析的完整 SHA 等于 `ExpectedCommit`。之后使用标签版本，从新的独立空缓存重新执行上述两种模式和三个消费者；脚本检查日志、版本和产物，人工再次完成标签与源码条目的对应检查。
6. 汇总提交和标签两组证据后才能报告对应版本远程可消费；远程构建成功、消费者编译通过和 Android/业务运行验收仍分别报告。

客户端取消、断网、超时或停止本地脚本，不保证 JitPack 已停止远程构建。应记录请求、时间、最后状态和未知结果；不能把取消写成远程停止，也不能把缺少日志、哈希或消费者结果写成通过。
